# Audit rules and tooling (VLTD application audit, 2026-10-18)

This audit INVENTORIES and TESTS the existing app. **It does not fix anything.** No app code, migrations, policies or redesigns. Findings go in `rows.jsonl` through the helper and are assembled into one report later.

## What the owner asked for (summary of the binding rules)
- Test BEHAVIOUR, not rendering. For each control: what does its label promise, what happens, is that the right result? A button being present is not a pass; an HTTP 200 is not proof; a filter must change eligible results (use fixtures that make that observable); a Save must persist after reload and, where relevant, in a clean second browser; Cancel must leave data unchanged; Delete must affect only the intended QA record; counts/values must match the records they describe; a loading failure must not pretend the collection is empty; an interactive-looking element that does nothing is a FAIL unless its disabled state is clearly explained; a carousel must move when dragged over its real cards/images.
- Use POPULATED fixtures, not empty pages. Cover (where relevant): signed out; unfinished onboarding; owner vs unrelated viewer; Personal vs Business; private/public/Guest View; empty / one-item / populated; valid / invalid / missing / explicit-zero inputs; successful save / refused save / interrupted connection; reload, direct URL, Back/Forward; desktop (1440) and phone (390) widths. Browser-emulated touch must be labelled "browser-emulated".
- Result vocabulary: **PASS / FAIL / BLOCKED / NOT TESTED**. BLOCKED = a tool/safety restriction stops that exact action (state which). NOT TESTED = not reached (state why). Never call something fully tested unless the rows support it.
- Keep FIRST-FAILURE evidence. Never overwrite it with a later pass. Investigate enough to tell a bad test from an app defect, but do not spend hours on each failure. Do not rewrite a test merely to make it green. If your first run fails because of YOUR test mistake, record that honestly (one row noting the test fix is fine) and rerun only the affected check.
- Separate genuine failures from proposed improvements ("I would design this differently" is not a failure). Improvements go in rows with result PASS or NOT TESTED and impact `improvement`, never FAIL.
- Group duplicate root causes in your write-up but keep every affected page/control as its own row (or list them in the row).

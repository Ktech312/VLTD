## New tests

`scripts/test-wants-handoff.ts` (npm script `test:wants-handoff`), 26 tests. It runs the real app code (wishlist, Following rules, refresh, Acquired, Upcoming Comics Want/Own) against a simulated browser, a fake account database that can go offline, and a fake comic catalog. No real accounts, network or providers. **12 of the 26 failed on the code as it stood this morning**; all pass after the fixes.

## Defects found and fixed (all in app code; no SQL)

1. **Want tap and Following described the same release differently.** A tap stored no series, no cover label, no identity of its own; numberless issues were titled "Name #"; a tap overwrote a hand-typed date and erased a date when the catalog gave none. Fixed in `comicWishlistModel.ts` (the pick now comes from the same function Following uses) and `wishlistModel.ts` (`setCatalogWish` keeps hand-edited fields and never erases a known date).
2. **A variant added on Upcoming was offered again on the Following card, and Add would have made a duplicate.** New `findWantForIdentity` and `addableSuggestion` in `wantsCore.ts`; used by `FollowTab.tsx` and `watchlist/page.tsx`.
3. **A skipped release was lit as "Want" on Upcoming and could be deleted by a tap, so it came back.** `loadComicStatuses` skips skipped records; `setCatalogWish(null)` never deletes a skipped or acquired record.
4. **Own on Upcoming Comics took the want off the list, and Following put the owned comic back.** A refresh now ignores releases already in the Vault (`planRuleRefresh` takes an owned-identities list; `pullRules.ts` supplies it from the Vault's catalog tags).
5. **A comic received through the Wishlist had no catalog tag, so Own could add it twice.** `wantAcquire.ts` now tags such Vault records `metron:<id>` (the same tag Own uses); `findOwnedComic` also finds older ones through the want's record of its Vault ids; an acquired want shows as Own on Upcoming.
6. **A pause (or edit, or new rule) not yet confirmed by the account was undone by the next sync.** `pullRules.ts` now keeps a small outbox on the device (same idea as the wishlist's): unconfirmed rules keep this device's copy and are sent again.

Files changed: `src/lib/wantsCore.ts`, `src/lib/pullRules.ts`, `src/lib/wishlistModel.ts`, `src/lib/comicWishlistModel.ts`, `src/lib/wantAcquire.ts`, `src/components/wants/FollowTab.tsx`, `src/app/watchlist/page.tsx`, `package.json` (one script), plus the new test and this note. No layout, navigation or billing change. No SQL needed, so nothing under `repair-batch-20/sql/`.

**Not verified on production** (by instruction, nothing was run there). The Vault tag in fix 5 relies on `vault_items.catalog_ref`, which `20261011_wishlist_comics_and_sharing.sql` adds; the older fallback (the want's own record of Vault ids) protects even if that column were missing. A short production re-check after deploy is worth doing for cases 4, 5 and 6.

## Unrelated findings (recorded, not fixed)

- **Remove is not Skip.** "Remove from list" on a want that Following added, or clearing the Want tap on Upcoming for a followed series, deletes it, and the next check adds it back as a new want. The Following tab says only that *skipped* releases never come back. Decision for you: should removing a followed release behave like Skip?
- **Stale dates the source cannot correct.** If a release moves outside the 180-day window, or the source drops its date, the catalog no longer reports it, so the entry keeps its old date (and eventually shows under "Release date has passed"). A want added by a Want tap with no Following rule on that series never gets date updates at all. Fixing this needs a per-issue lookup, which is new work and new catalog load.
- **A Want tap on a skipped release still lights up** until the page refreshes (nothing is saved, by the existing rule that a tap does not un-skip). Cosmetic.
- **A unique-index clash during a wishlist upload is misread as "missing column"** (`isMissingColumn` in `wishlistModel.ts` matches "constraint"), so the upload would silently fall back to a lower column set and skip the newer fields. It cannot happen on the normal paths (the duplicate checks above prevent it), but the error handling is too broad.
- **All Metron variants get the same label, "Variant cover"**, because the source does not give a description; variants are told apart by their title (4B, 4C) only.
- **Variant suggestions are lost on reload** (they exist only after a check runs; checks are at most every 6 hours per rule unless you press Check now).
- Upcoming "Own" still records the cover price as the price paid (already listed as a decision in the Wishlist closeout).
